# 예상 질문과 답

[← README](../../README.md) · [기술 구조](architecture.md) · [서버 권위 원정과 보안](server-authority.md) · [실시간 동기화](realtime.md) · [인프라와 배포](infra.md) · [트러블슈팅](troubleshooting.md)

최종 발표를 준비하면서 정리한 예상 질문과 답입니다. 숫자는 저장소의 코드와 커밋, 분석 리포트로 확인했습니다.

## 로딩과 그림

### 1. 이미지 용량은 53% 줄었는데 로딩은 왜 68% 줄었나요?

원정 이미지는 246MB에서 116MB로 53% 줄었고, 챕터 입장 시간은 25초에서 8초로 68% 줄었습니다.

둘은 용량과 대기 시간이라는 서로 다른 지표입니다. 무손실 WebP로 바꾸면서 필요한 그림만 받도록 묶음도 나눴기 때문에, 대기 시간이 용량과 같은 비율로 줄어들 필요는 없습니다.

다만 두 변경이 각각 얼마나 줄였는지는 따로 재지 않았습니다.

### 2. 왜 무손실 WebP인가요? 손실 압축이나 AVIF는요?

저희 게임 그림은 도트 그림이라 픽셀 하나만 바뀌어도 바로 티가 납니다. 그래서 화질을 깎는 손실 압축 대신, 그림을 한 픽셀도 바꾸지 않는 무손실 WebP를 골랐습니다.

실제로 변환한 그림을 PNG와 디코드해서 비교해 보니 차이가 0이었고, 그러면서도 원정 그림 묶음은 246MB에서 116MB로 절반 이하로 줄었습니다.

AVIF 를 따로 물으면: AVIF는 이번에 따로 비교하지 않았습니다. 도트 그림이라 무손실이 먼저였고, 무손실 WebP만으로도 용량이 절반 이하로 줄었습니다. AVIF 비교는 다음 개선 과제로 보고 있습니다.

### 3. 변환은 언제, 어디서 하나요?

변환은 게임을 빌드할 때 합니다. 빌드 스크립트가 sharp 라이브러리로 그림 묶음 안의 PNG를 무손실 WebP로 바꾸는데, 여섯 장씩 병렬로 돌리고 PNG 내용의 해시로 결과를 캐시해 두어서, 다음 빌드부터는 바뀐 그림만 다시 만듭니다. 처음 전체를 변환할 때는 959장에 23초 정도 걸렸습니다.

PNG 파일은 지우지 않고 남겨 둡니다. React나 CSS가 PNG 주소를 직접 쓰는 UI 그림이 있어서, 게임 묶음 안의 주소만 WebP로 바꿉니다.

또 작은 낱장 그림은 WebP가 오히려 더 크면 PNG를 그대로 쓰고, 변환에 실패해도 PNG로 돌아가게 해서 빌드나 게임이 멈추지 않게 했습니다.

## 구조와 기술 선택

### 4. shared는 왜 필요한가요?

shared에는 콘텐츠 JSON과 데이터 검증, 그리고 화면에 의존하지 않는 체력 · 의태 · 드랍 같은 규칙을 한곳에 모아 두었습니다.

이게 없으면 클라이언트 여러 기능에서 같은 정의가 중복되고, 고칠 때 서로 어긋나기 쉽습니다.

Java 서버는 TypeScript 코드를 직접 실행한 것이 아니라 같은 콘텐츠 JSON을 읽었습니다.

대안으로는 규칙을 따로 구현하거나 계약에서 타입을 자동 생성하는 방식이 있는데, 각각 동기화 작업과 도구를 만드는 비용이 듭니다.

> 참고: 지금 itch판에서도 클라이언트의 규칙 · 콘텐츠 검증에 shared를 그대로 씀

### 5. 게임 엔진 대신 Phaser를 쓴 이유는요?

먼저 표현을 바로잡으면, Phaser도 2D 웹 게임 프레임워크이자 엔진입니다.

횡스크롤 2D 게임을 TypeScript, React와 함께 브라우저에서 바로 실행하고, HTML 빌드로 배포하기에 맞았습니다.

대신 브라우저의 성능 · 메모리 제약을 받고, Unity 같은 편집기 중심의 제작 도구는 직접 구성해야 합니다.

또 전투가 클라이언트에 있으니, 위조 방지는 서버가 검증할 수 있는 범위로 제한됩니다.

### 6. Phaser와 React를 왜 같이 쓰나요?

전투와 물리는 Phaser가, 창과 HUD 같은 UI는 React가 맡습니다.

둘 사이는 상태 저장소(zustand)로 이어서, 전투가 체력 · 쿨타임 같은 상태를 쓰면 HUD가 그것을 읽어 그립니다.

대신 상태를 연결하는 일과, 창이 열렸을 때 게임을 일시정지시키는 동기화가 관리 비용으로 남습니다.

### 7. 전투 중에도 서버와 통신하나요?

전투 중에는 통신하지 않습니다. 방에 들어갈 때 체크포인트를 저장하고, 방을 클리어할 때 쓰러뜨린 몹 목록, 주운 드랍, 남은 체력, 골드를 얻은 기록, 포션 수를 한 번에 보내 정산합니다.

그래서 네트워크 상태가 전투 손맛에 영향을 주지 않고, 중간에 연결이 끊기면 그 방에 들어간 지점부터 다시 시작합니다.

예외는 일시정지와 재개입니다. 랭킹 시간에서 멈춘 시간을 빼기 위해 바로 알리는데, 이때도 시각은 클라이언트가 아니라 서버가 직접 기록합니다.

> 참고: 싸우는 중에 주운 드랍은 클리어 요청에 함께 실음, 포션 저장도 싸움이 끝난 방에서만

### 8. 멀티 콘텐츠마다 동기화를 어떻게 했나요?

콘텐츠마다 공정성이 얼마나 중요한지에 따라 방식을 다르게 했습니다.

광장은 싸움이나 보상이 없어서, 각자 보낸 모습을 서버가 초당 15번 모아 중계하고, 받는 쪽은 120밀리초 전 시점으로 보간해 부드럽게 보여 줍니다.

PvP는 공정성이 가장 중요해서 서버 권위 방식으로 만들었습니다. 이동, 평타, 피격, 체력은 서버가 계산하며, 스킬 맞힘 보고도 두 사람 사이 거리로 서버가 다시 검증합니다.

협동 생존은 같은 편끼리 하는 모드라 방장 브라우저가 몹을 계산하는 호스트 권위 방식을 썼습니다.

라인 전쟁은 초당 20틱 락스텝으로, 서버가 명령을 세 틱 뒤에 실행되도록 중계하고 양쪽 상태의 해시만 비교합니다.

> 참고: PvP 경기장은 입력만 받아 서버가 이동까지 계산, 던전처럼 하는 대전은 클라이언트가 자리를 보내고 서버가 맞힘을 거리 · 무적 · 아군 · 상한으로 검증

### 9. 밸런스 수치를 고치면 배포는 어떻게 되나요?

밸런스 수치는 shared/data의 JSON 파일 하나에 있고, 클라이언트와 서버가 같은 파일을 읽습니다.

수치는 빌드할 때 클라이언트 · 서버 이미지에 같이 들어가므로, 고치면 다시 빌드해서 배포합니다. develop에 병합하면 Jenkins가 개발 서버에 자동으로 배포하고, 운영은 main에 병합한 뒤 Jenkins에서 직접 빌드를 눌러 내보냅니다.

이미 열려 있던 게임 화면은 60초마다 콘텐츠 해시를 확인해 업데이트를 알리고, 판이 다르면 새 원정 시작을 막습니다. 진행 중이던 원정은 새 판으로 옮기거나 포기를 고르게 합니다.

배포 방식이 무중단이 아니라서 API가 약 15초 끊깁니다.

## 보안과 조작 탐지

### 10. 시드가 같으면 플레이 결과도 항상 같나요?

시드는 맵과 보상 선택을 재현하기 위한 값입니다. 같은 시드면 방 구성, 몹 배치, 드랍, 상점이 같게 나옵니다.

하지만 전투는 플레이어 입력에 따라 달라지고, 프레임 시간과 치명타 확률도 시드 밖에 있어서, 같은 시드라도 플레이 결과까지 같아지지는 않습니다.

플레이어 입력까지 같게 재현하는 전투 재현과는 구분해야 합니다.

### 11. 클라이언트 전투 결과를 조작하면 서버가 막을 수 있나요?

서버가 직접 계산하는 보상과, 검증할 수 있는 요청은 서버가 확인합니다. 쓰러진 몹 목록이 계획과 같은지, 방마다 최소 2초가 지났는지, 더미 몹을 건드리지 않았는지를 보고, 시간도 서버 시계로 잽니다.

하지만 서버가 전투를 다시 돌려 보지는 않기 때문에, 브라우저에서 일어난 전투 자체가 진짜인지 완전히 증명할 수는 없습니다.

> 참고: 그래서 남은 조작은 방 기록 → 규칙 검사 → AI 점수 → GM 판정으로 찾는 2차 대응을 둠

### 12. 더미(허니팟) 몹은 어디에, 어떤 규칙으로 놓나요?

더미 몹은 실제 맵 위에 놓는 게 아니라, 서버가 방마다 내려주는 몹 목록에만 한 마리씩 끼워 넣습니다. 그 몹은 맵에 자리가 없어서 정상 클라이언트는 받자마자 빼고 그리지 않습니다. 그래서 정상적으로 플레이해서는 절대 건드릴 수 없습니다.

핵심은 목록만 보고는 골라낼 수 없게 진짜 몹처럼 만드는 것입니다. 다른 방 맵에 있는 진짜 몹의 자리 이름과 몹 종류를 빌려 오고, 드랍도 그 방의 드랍표대로 진짜처럼 정합니다.

자리 이름은 맵의 번호를 자연스럽게 이어 붙입니다. 예를 들어 P01부터 P05까지 있는 방이면 P06이나 다른 글자의 1번을 쓰고, 번호를 건너뛰지 않습니다. 번호를 잇는 경우와 새 글자를 쓰는 경우를 반반으로 섞어서, 가장 큰 번호를 빼는 식의 요령도 통하지 않게 했습니다.

목록 안 위치도 맨 앞만 피해서 무작위로 두고, 따로 저장하지 않고 원정 시드와 방 번호로 매번 같은 더미를 다시 만들어 냅니다.

실제로 첫 버전은 더미가 늘 같은 몹에 드랍도 없어서 콘솔에서 바로 걸러졌고, 다음 날 지금 방식으로 바꿨습니다.

> 참고: 자리 이름 규칙은 1챕터 기준: 2 · 3챕터는 맵 번호가 띄엄띄엄이라 비운 번호 · 가장 큰 번호 다음 중 하나

### 13. 화면에도 없는데 「건드린다」는 게 무슨 뜻인가요?

여기서 건드린다는 건, 클라이언트가 서버로 보내는 요청에 더미 몹이나 그 드랍의 id가 들어온다는 뜻입니다. 정상 클라이언트는 더미를 그리지 않으니 보낼 일이 없고, 서버가 준 목록을 그대로 다 잡았다고 보내는 스크립트만 여기에 걸립니다.

방 클리어, 드랍 수령, 매복 보상에서 걸리면 그 원정은 바로 무효가 되고 보상은 하나도 정산되지 않습니다. 어떤 계정이 어느 방에서 무엇을 건드렸는지 DB에 기록되고, 서버 로그와 모니터링 지표에도 남습니다. 계정을 자동으로 정지하지는 않습니다.

### 14. 왜 처음부터 서버가 전투를 판정하지 않았나요?

저희 게임은 브라우저에서 돌아가는 실시간 액션이라, 서버가 전투를 똑같이 판정하려면 플레이어 입력을 계속 서버로 보내고 서버도 물리와 전투를 그대로 시뮬레이션해야 합니다. 그러면 서버 비용과 입력 지연이 크게 늘어서, 싱글 원정은 서버가 결과를 다시 검증하는 방식을 택했습니다.

대신 나중에 서버 판정을 붙일 수 있도록 체력 · 의태 · 유물 같은 전투 규칙을 화면 코드와 분리해 shared에 두었습니다. 공정성이 가장 중요한 PvP는 실제로 서버가 직접 판정하고 있습니다.

### 15. 왜 k-NN인가요? 지도 학습이나 Isolation Forest는요?

조작 기록에는 정답 라벨이 없어서, 정상 기록만으로 학습하는 비지도 방식을 골랐습니다.

처음 설계는 Isolation Forest였는데, 학습 범위를 크게 벗어난 조작을 잘 잡지 못했습니다. 예를 들어 속도 2배 조작을, 정상 기록의 1%만 검토한다고 할 때 Isolation Forest는 2%밖에 못 잡았고 k-NN은 93%를 잡았습니다.

k-NN을 포함해 비지도 모델 일곱 가지를 같은 조건으로 비교했더니 AUC가 0.76에서 0.79 사이로 비슷했습니다. 그중에서 이 기록과 가장 비슷한 정상 기록을 GM에게 바로 보여 줄 수 있는 k-NN을 선택했습니다.

반대로 조작 데이터로 배우는 지도 학습은, 배운 적 없는 조작에 AUC 0.53으로 거의 찍는 수준이었습니다.

> 참고: 출처: 개발 서버 기록 · 만든 조작 기준. Isolation Forest 평균 AUC 0.67

### 16. 특징은 무엇인가요?

방 하나마다 특징 열 개를 씁니다. 시간 쪽은 클리어 시간과, 게임 안 시계를 서버 시계로 나눈 시계 비율입니다. 피해 쪽은 초당 피해, 평균 한 방, 가장 센 한 방, 몹 하나당 깎은 체력, 받은 피해 속도이고, 처치 쪽은 처치 비율, 첫 처치까지 걸린 시간, 처치 간격이 얼마나 고른지입니다.

맵과 스테이지마다 기준이 다르기 때문에, 같은 챕터 · 스테이지 · 방 종류끼리 묶어 중앙값과 MAD로 표준화합니다. 이때 의심스러운 방향만 보고 반대쪽은 0으로 잘라서, 단순히 플레이를 못하는 사람은 목록에 뜨지 않게 했습니다.

그리고 가장 가까운 정상 방 다섯 개까지의 평균 거리를 구해, 정상 기록 중 상위 몇 퍼센트인지로 바꿔 점수로 씁니다.

> 참고: 시계 비율만은 묶음 중앙값 대신 고정 기준 0.96 을 씀: 쉬다 온 방이 중앙값을 끌어내리기 때문
